# API spec for the SDK: Holdstation Pay partner API

Sources: vendor OpenAPI 3.1 (`info.title` "Holdstation Pay", `info.version` "1.0", 44 operations) and the vendor markdown pages (pay-docs.holdstation.com). "OpenAPI" below means the JSON file, "guide" means its `info.description`, "md" means a markdown page. Where they disagree, both are quoted and the item is marked `UNCONFIRMED`. Nothing here was verified against a live server.

Notation in tables: `*` = required per OpenAPI, `?` = optional, `str` string, `int` integer, `dec` money/rate (see Money), `ts` = `Timestamp`. Auth column: `public` = no key required, `key` = `Partner-App-Key` only, `key+sig` = `Partner-App-Key` plus Ed25519 signature.

## 2. Authentication

### 2.1 API key

- Header: `Partner-App-Key: <key>`. OpenAPI security scheme `partner-app-key` (`apiKey`, in header).
- Required on every operation except the public ones marked in section 4. The vendor's own example sends the header to the public `GET /api/v1/tokens`, so the SDK always sends it.

### 2.2 Ed25519 request signing ("Signed API")

| Item | Value |
|---|---|
| Headers | `Partner-App-Key`, `X-HSPay-Signature`, `X-HSPay-Timestamp` ("all three signed-request headers must be present on every signed request") |
| Signed string | `sign_data = sorted_query_string + "\n" + body + "\n" + timestamp` |
| `sorted_query_string` | "query parameters sorted alphabetically by key, formatted as `key1=value1&key2=value2`. Empty string when there are no query parameters." No leading `?`. The vendor Go example builds it from `url.Values` with `k + "=" + query.Get(k)`: decoded value, first value only, no URL-encoding. |
| `body` | "the raw request body (byte-for-byte). Empty string for requests with no body." |
| `timestamp` | Unix seconds as a decimal string; the same value goes in `X-HSPay-Timestamp`. |
| Tolerance | "Must be within **60 seconds** of the server time" |
| Algorithm | Ed25519 (pure, no prehash) over the UTF-8 bytes of `sign_data` |
| Signature encoding | Base64 standard alphabet with padding (`base64.StdEncoding`), in `X-HSPay-Signature` |
| Private key format | Vendor Go example: base64 std of the 64-byte Go `ed25519.PrivateKey` (seed followed by public key). |
| Public key format (`verify_key`) | Base64 std of the raw 32-byte public key. |
| Method and path | Not part of the signed string. |

SDK rules that follow from this (skill section 4):
- Encode the JSON body once, sign those bytes, send those bytes.
- For a signed request with no body (all GET, DELETE, and the POSTs with no body in section 4) sign the empty string and send no body.
- Build the query once from sorted keys; sign `key=value` with the unescaped value and send the same pairs URL-encoded.
- Clock is injectable (`now`).
- Accept the private key as base64 of 64 bytes (seed+public), 32 bytes (seed) or 48 bytes (PKCS#8 DER). Reason: the vendor shell example `openssl pkey -outform DER | tail -c 64 | base64` outputs the whole 48-byte PKCS#8 DER, not 64 raw bytes.

UNCONFIRMED: whether the server canonicalises query values decoded or as sent on the wire. It matters only for free-text values (`token`, `reference_id`).

### 2.3 Registering and rotating the public key

- Initial: "provide your public key to the Holdstation team directly — they will register it on your account."
- Rotation: `POST /api/partners/verify-key` (md "Upload Public Key") or `POST /api/signed/partners/verify-key` (guide 9.5), body `{"verify_key": "base64EncodedEd25519PublicKey"}`, signed with the current private key; "subsequent requests must be signed with the new private key". This endpoint is not in the OpenAPI paths. UNCONFIRMED: the real path. Not part of the 44 operations.

## 3. Response shapes

### 3.1 Success envelopes

| Shape | Body | Used by |
|---|---|---|
| A. Standard | `{"message": "success", "data": {...}}` | Everything unless listed under B or C |
| B. Standard + business result inside `data` | `{"message": "success", "data": {"success": true, "code": 0, "error": "", ...payload}}` | `POST /partners/orders/withdraw`, `.../confirm-withdraw`, `.../crypto-payout`, `POST /partners/orders/{order_id}/close`, `GET .../customer-info`; KYC (`success` only, no `code`/`error`) |
| C. Bare per OpenAPI (no `message`/`data` wrapper) | the payload object itself | `GET /partners/funds`, `GET /partners/funds/balance`, `POST /partners/funds/convert`, `GET /partners/funds/logs`, `GET /partners/funds/logs/{fund_log_id}` (each `{success, code, error, ...}`), `GET /partners/funds/deposit-addresses` (`{success, deposit_addresses, ...}`), `GET` and `POST /partners/webhook-url` (`{webhook_url}`), `POST /partners/payment-methods/qr/decode` (`{data, error, error_code, message}`) |

UNCONFIRMED: shape C. OpenAPI and guide 10.2 show these 9 bodies bare; every md example shows them inside shape A (`{"message":"success","data":{...}}`; for QR decode that gives `data.data`). The existing integration reads the funds endpoints as wrapped.

Real examples (md):

```json
{"message":"success","data":{"rate":{"buy":"25850","sell":"25750"}}}
```
```json
{"message":"success","data":{"success":true,"code":0,"error":"","funds":[{"id":1,"partner_id":"partner-xyz","token":"USDT","balance":"1000.50","updated_at":{"seconds":1700000000,"nanos":0}}]}}
```
```json
{"message":"success","data":{"success":false,"code":3,"error":"customer info not yet available","customer_info":null}}
```

| Endpoint(s) | `code` | Name | Meaning |
|---|---|---|---|
| withdraw, confirm-withdraw | `1` | `INVALID_INPUT` | body failed validation |
| | `2` | `PARTNER_NOT_FOUND` | partner cannot be resolved |
| | `3` | `INSUFFICIENT_BALANCE` | fund balance below amount + fees |
| | `4` | `DUPLICATE_REQUEST` | `idempotency_key` already used |
| | `5` | `ORDER_NOT_FOUND` | confirm only |
| | `6` | `ORDER_NOT_OWNED_BY_PARTNER` | confirm only |
| | `7` | `INVALID_ORDER_STATE` | already confirmed, expired or closed |
| | `8` | `INVALID_ORDER_TYPE` | confirm only |
| | `9` | `WITHDRAW_CODE_ORDER_TYPE_NOT_AVAILABLE` | order type blocked for the partner (withdraw) |
| | `11` | `WITHDRAW_CODE_UNDER_MAINTENANCE` | maintenance window |
| | `99` | `INTERNAL_ERROR` | "safe to retry after a short backoff" |
| crypto-payout | `12` | `CRYPTO_PAYOUT_CODE_UNDER_MAINTENANCE` | maintenance window |
| customer-info | `0` / `2` / `3` | `SUCCESS` / `NOT_SUPPORTED` / `NOT_AVAILABLE` | `2`, `3` are states, not faults |
| QR decode (`error_code`, int) | `1` / `2` / `3` / `4` | | invalid input / image download failed / image decode failed / parse failed |

Proposed SDK rule: HTTP 2xx with `success == false` returns `*APIError{Status: 200, Code: "<code>", Message: <error>}` with the raw body kept, except `GetOrderCustomerInfo` and `DecodeQR`, which return the envelope fields to the caller.

### 3.2 Error body (status 400 and above)

OpenAPI declares the same inline schema for 400, 401, 500 on all 44 operations (the `ErrorModel` component is referenced by none):

```json
{"error": "string", "error_code": "string", "message": "string", "detail": "string"}
```

Real examples (md):

```json
{"error":"unauthorized","error_code":"UNAUTHORIZED","message":"Invalid or missing API key"}
```
```json
{"error":"not found","error_code":"NOT_FOUND","message":"No fund log with this ID"}
```
```json
{"error":"VALIDATION_FAILED","message":"One or more fields are invalid","detail":"{\"code\":\"VALIDATION_FAILED\",\"details\":[{\"code\":\"MISSING_FIELD\",\"target\":\"/persons/0/date_of_birth\"},{\"code\":\"FILE_TOO_LARGE\",\"target\":\"/documents/2/files/0\"}]}"}
```

- Request id: none documented, in body or headers.
- `detail` on 422 is a JSON-encoded string: `{"code":"VALIDATION_FAILED","details":[{"code":"...","target":"<JSON pointer into the request body, 0-based, empty for the whole body>"}]}`.
- KYB errors carry the code in `error` and have no `error_code` (`VALIDATION_FAILED`, `CONFLICT`, `UNSUPPORTED_MEDIA_TYPE`, `NOT_FOUND`). SDK: `APIError.Code` = `error_code`, falling back to `error` when `error_code` is empty; expose parsed `Details []ErrorDetail{Code, Target}` when `detail` parses.

| Status | Documented for |
|---|---|
| `200` | success (and business failures, 3.1) |
| `201` | KYB submit per md; OpenAPI says `200`. UNCONFIRMED |
| `400` | bad request; malformed id; oversized body on KYC (32 MB) and KYB (40 MB), "not `413`" |
| `401` | missing/invalid API key, signature or timestamp |
| `403` | IP not on the allowlist |
| `404` | unknown or foreign id: deposit VA, fund log, KYC, KYB; expired/unknown withdraw order (md example) |
| `409` | KYC id exists; KYB Pending/Approved record exists |
| `415` | file/image type not accepted (KYC, KYB) |
| `422` | KYC image or KYB field validation failed |
| `500` | server error |
| `429` | "not implemented" for KYB; not mentioned elsewhere |

`error_code` values seen in the docs: `BAD_REQUEST`, `UNAUTHORIZED`, `NOT_FOUND`, `INSUFFICIENT_BALANCE`, `ORDER_EXPIRED`, `ORDER_NOT_FOUND`, `INVALID_TOKEN`, `KYC_ALREADY_EXISTS`, `KYC_NOT_FOUND`, `400105` (order type not available: deposit, withdrawal), `400110` (under maintenance: deposit, withdrawal). `MISSING_REQUIRED_FIELD` is named for KYC without saying which field carries it.

Validation detail codes: `MISSING_FIELD`, `INVALID_FORMAT`, `MISSING_DOCUMENT`, `INVALID_DOCUMENT_TYPE`, `MISSING_LEGAL_REPRESENTATIVE`, `FILE_TOO_LARGE`, `FILE_CORRUPT`, `FILE_ENCRYPTED`, `MEDIA_TYPE_MISMATCH`.

UNCONFIRMED: the md 400/404 examples for withdraw and confirm-withdraw (`INSUFFICIENT_BALANCE`, `ORDER_EXPIRED`, `ORDER_NOT_FOUND` as HTTP errors) contradict the prefunding guide (HTTP 200 with `code`).

## 5. Types

Nothing in the order, bank, token and fund schemas is marked required in OpenAPI: any field may be absent. Object-valued fields are pointers in Go. Unknown enum values must decode without error (named `int`/`string` types with constants).

`KYBFileInput`: `filename*` str, `content_type*` (`application/pdf` \| `image/jpeg` \| `image/png` \| `image/heic`), `data*` base64 std (at least 1 byte, must match `content_type`, no encrypted PDF).

`KYB` (response): every submitted field at the same path, plus `id*` str, `partner_id*` str, `status*` int (`KYBStatus`: `1` Pending, `2` Approved, `3` Rejected), `rejection_reason*` str (empty unless status 3), `submitted_at*`, `created_at*`, `updated_at*`, `reviewed_at?` (null while pending). Files come back as `file_ref*` (`f_` + 12 hex), `filename*`, `content_type*`, `size*` int64; `data` is never returned. OpenAPI person view also has `id_card_front`, `id_card_back`, `selfie` file views.

## 7. Webhooks (`webhook.go`)

### 7.1 Deliveries

| | Order status | Fund balance change | VA / MID payment callback |
|---|---|---|---|
| Topic | `pay.order.status-updated` | `pay.partner.fund-balance-changed` | none |
| Destination | per-order `callback` (must be HTTPS) | partner `webhook_url` (`POST /partners/webhook-url`) | `va_callback` URL (4.6) |
| Method | POST | POST | POST |
| `Content-Type` | `application/json` | `application/json` | `application/json` |
| `User-Agent` | `HSPay-Webhook-Dispatcher/1.0` | `HSPay-Webhook-Dispatcher/1.0` | `HSPay-Callback-Dispatcher/1.0` |
| Topic header | `X-HSPay-Event-Topic` | `X-HSPay-Event-Topic` | none |
| Signature header | `X-HSPay-Event-Signature` | `X-HSPay-Event-Signature` | `X-HSPay-Response-Signature` |
| Expected response | HTTP `200` within 30 s | HTTP `200` within 30 s | not documented |
| Retry | up to 5 times; intervals 1, 2, 4, 8, 12 s; then marked failed | up to 5 times; "exponential backoff: 1, 2, 4, 8, up to 30 seconds maximum"; then abandoned | not documented |

### 7.2 Signature verification (all three)

- Ed25519 over the entire raw request body, exactly as received.
- Signature: base64 standard, in the signature header.
- Key: the "Webhook Checksum Key" / `checksum_key` (base64 Ed25519 public key; "derived public key from the partner's `sign_key`", a key held by Holdstation). It is not the request-signing key pair.
- Vendor Go example decodes the key as the raw 32-byte public key; the vendor Java example loads it as `X509EncodedKeySpec` (44-byte SPKI DER). UNCONFIRMED which is issued; the SDK accepts both lengths.
- No timestamp or replay window is documented. Deduplicate on envelope `id`.
- No vendor test vector.

### 7.3 Envelope and payloads

Envelope (order and balance): `id` str (UUID), `topic` str, `ts` str (RFC 3339), `payload` object. Deprecated aliases `type` and `timestamp` may still be present ("will be removed in a future version").

Order payload:

| Field | Type | Notes |
|---|---|---|
| `order_id` | str | |
| `old_order_state`, `new_order_state` | int | `OrderState` |
| `old_order_processing_state`, `new_order_processing_state` | int | absent in the Refunded example |
| `tx_hash` | str, optional | onramp Completed: transfer to the user; Refunded: refund transfer |
| `chain_id` | number, optional | sent together with `tx_hash` |
| `scan_url` | str, optional | omitted when the chain has no known explorer |

Balance payload:

| Field | Type | Notes |
|---|---|---|
| `partner_id` | str | |
| `token` | str | e.g. `USDT`, `VND` |
| `pre_balance`, `post_balance`, `change_amount` | str (money) | |
| `change_type` | int | `FundChangeType` (5.4) |
| `fund_log_id` | int | fetch details with `GetFundLogByID` |

UNCONFIRMED: `deposit_va_id` in the balance payload (the OpenAPI text for create deposit VA says the webhook "reports it with deposit_va_id"; the payload examples and the md note "The payload carries no metadata" say otherwise).

VA payment callback body (no envelope): `va_account`, `va_account_name`, `va_account_addr`, `va_bank_name`, `transfer_content` (base64), `amount` (str), `time_paid` (str, Unix seconds), `transaction_id` (all strings). Excluded upstream fields: `mc_fee`, `order_id`, `cashin_id`, `client_request_id`, `merchant_id`, `secure_code`.
